# A · 화면에 들어갈 실제 데이터 만들기

담당자: 미정. 코드보다 자료 확인이 중심입니다. 목표는 카드와 상세 패널에 표시할 실제 구매 기록과 근거를 준비하는 것입니다.

## 만들어서 전달할 것

| 만들 파일 | 넣을 내용 |
|---|---|
| `data/demo/purchases.json` | 실제 구매 기록 배열 |
| `data/demo/market-prices.json` | 확인된 시중가 배열. 없으면 빈 배열 |
| `data/sources/purchases.md` | 출처·이용 조건·필드 대응표 |
| `docs/evidence/data-check.md` | 원본 대조 결과와 모르는 조건 |

## 작업 순서

### 1. 같은 제품의 구매 자료 찾기

공식 공공데이터에서 물품 구매 자료를 찾습니다. 제품 식별번호·모델·규격으로 같은 물품인지 확인합니다. 기관명·구매일·수량·단가가 있는 행을 골라 E와 B에게 보여줍니다. “계약금액”을 단가로 착각하지 않도록 원본 설명도 함께 보냅니다. 서로 다른 기관 자료를 확보할 수 없으면 바로 알립니다.

### 2. 원본과 내부 필드 대응표 만들기

`purchases.md`에 `원본 열 이름 → 내부 이름 → 의미`를 적습니다. 내부 이름은 [데이터 계약](../contracts/data-model.md)을 사용합니다. 카드에 필요한 `item_name`(품목명)도 추가하도록 E와 맞춥니다. 날짜·금액·단위가 애매하면 임의 해석하지 않습니다.

### 3. JSON 작성하기

E에게 공통 JSON 예제를 받고, 확인한 실제 값으로 채웁니다. 큰따옴표·쉼표 때문에 어렵다면 원본 표와 대응표를 E에게 전달해 변환 도움을 받습니다. record_id는 중복되지 않게 하고, 모르는 값은 null로 둡니다. 원본 ID와 출처를 삭제하지 않습니다. 연락처 등 불필요한 개인정보는 넣지 않습니다.

파일 생성 뒤 저장소 루트에서 `python3 -m json.tool data/demo/purchases.json`을 실행합니다. Windows에서는 E가 확인한 Python 명령을 사용합니다. 에러 없이 출력되는 것은 문법만 맞다는 뜻이므로 다음 대조 작업도 해야 합니다.

### 4. 한 행씩 대조하기

시연할 모든 행의 기관·제품·가격·수량·날짜를 원본과 비교합니다. 취소 기록과 같은 계약의 변경 이력이 중복 구매처럼 들어가지 않게 합니다. 배송·설치·세금 포함 여부는 확인된 만큼만 기록합니다. 확인 결과를 data-check.md에 적습니다.

### 5. 시중가 근거 준비하기

동일 모델의 판매처, 가격, 통화, 단위, 확인 날짜, 원본 URL, 세금·배송·설치 조건을 별도로 기록합니다. 제품명이 비슷한 것만으로 같은 제품이라고 하지 않습니다. 자료가 없으면 빈 배열을 넘기고 시중가 없음 상태를 확인합니다.

### 6. 화면 확인과 전달

B·E에게 두 JSON과 출처 문서를 넘깁니다. D의 카드와 패널을 열어 원본과 숫자가 같은지 확인합니다. 발표용으로 “무슨 자료를 언제 받아 무엇을 비교했는지” 세 문장을 정리합니다.

## 완료 확인

- [ ] JSON 문법 검사와 원본 대조를 모두 했다.
- [ ] 출처·기준일·이용 조건을 기록했다.
- [ ] 없는 시중가와 포함 조건을 만들어내지 않았다.
- [ ] 화면에서 시연할 모든 구매 건의 근거를 찾을 수 있다.

## 막혔을 때 전달할 내용

어느 단계인지, 파일 경로, 입력, 기대 결과, 실제 오류를 E와 관련 담당자에게 전달합니다. 인증키는 지웁니다. 없는 데이터나 기능을 완료된 것처럼 만들지 않습니다. [공통 역할 안내](README.md)와 [완성 화면 명세](../screen-spec.md)를 기준으로 확인합니다.
